# 技術スタック・ディレクトリ構成

## 最低限の技術スタック

| 技術 | 用途 |
| --- | --- |
| TypeScript | UI・ゲーム進行・描画処理の実装と型定義 |
| React・React DOM | ページ、会話表示、選択肢、操作部品の描画 |
| Three.js | 3Dシーン、カメラ、ライト、背景の描画 |
| @pixiv/three-vrm | VRMモデルの読み込み・表示・更新 |
| Vite | 開発サーバーと配布用ビルド |
| CSS | レイアウト・装飾・画面サイズへの対応 |
| localStorage | 小さな進行データと設定のブラウザ内保存 |
| Node.js・npm | 開発ツールの実行と依存パッケージ管理 |

状態管理はReactの標準機能から始める。Three.jsは直接利用し、React側の表示部品で描画の開始・終了を管理する。最初はルーティング、外部状態管理、UIライブラリ、バックエンド、データベースを追加しない。

## 大まかなディレクトリ構成

```text
app/
├── public/
│   └── assets/
│       ├── models/
│       └── backgrounds/
└── src/
    ├── pages/
    ├── components/
    │   ├── controls/
    │   ├── dialogue/
    │   └── stage/
    ├── services/
    ├── utils/
    ├── types/
    ├── scenarios/
    └── styles/
```

## 各ディレクトリの役割

| ディレクトリ | 役割 |
| --- | --- |
| public/assets/ | VRMモデル・背景などの静的素材 |
| src/pages/ | ページ単位のレイアウト、画面状態の管理、部品とサービスの接続 |
| src/components/controls/ | ボタン、選択肢、セーブ操作などの操作部品 |
| src/components/dialogue/ | 台詞・話者名などの会話表示部品 |
| src/components/stage/ | 3D描画領域をReactに接続する表示部品 |
| src/services/ | シナリオ進行・分岐判定、保存・復元、素材読み込み、Three.js・VRMの描画管理 |
| src/utils/ | 文字列・数値・パスなどを扱う、画面やゲーム状態に依存しない補助関数 |
| src/types/ | シナリオ・進行状態・保存データなど、複数箇所で共有する型 |
| src/scenarios/ | 台詞・選択肢・分岐・表示指示などのシナリオデータ |
| src/styles/ | 共通スタイルと各画面・部品のスタイル |

## 分割の方針

- ページは部品を組み合わせ、コントロールは表示値と操作時のコールバックを受け取る。
- サービスとユーティリティはReact・ページ・UI部品を参照しない。
- サービスは処理結果やエラーを返し、画面への反映はReact側で行う。
- 描画サービスは描画先を外から受け取り、ページの要素を自分で探さない。
- Three.js・VRMの毎フレーム更新は描画サービス内で行い、Reactには会話や選択肢などのUI状態を持たせる。
- 状態や外部機能を扱う処理はサービス、状態を持たない汎用的な変換・計算はユーティリティに置く。
- 型や補助処理は、共有が必要になるまでは利用箇所の近くに置く。
- 小さな構成から始め、部品や処理が増えてからサブディレクトリを追加する。
- app内で依存パッケージ・ビルド設定・素材を完結させ、既存ソースは参考にしてもapp外への実行時依存を作らない。

## シナリオ設計・テスト容易性方針 (Headless Engine)

- **画面非依存のステートマシン**:
  - シナリオ進行・分岐判定・フラグ制御を担うシナリオエンジン（`src/services/scenario/`）は、React・Three.js・DOM・ブラウザAPIに一切依存しない純粋なTypeScriptロジックとして設計する。
  - UIや3D描画は「エンジンの状態（現在の台詞、話者、演出指示、選択肢など）」を受け取って描画するだけの購読者（Subscriber）とする。
- **シナリオ単体テストの自動化**:
  - 画面を起動することなく、Vitest等のNode環境で「選択肢の選択」「テキスト送り」「フラグ条件判定」「特定エンディングへの到達性」をプログラムから自動テスト・網羅シミュレーションできるようにする。
  - 不正な分岐先指定（存在しないシーンIDへのgoto等）や未定義フラグ参照を検知する静的検証バリデータも用意する。

## 多言語（i18n）設計（単一インスタンス・統合構造）

- **既存の課題（二重管理の廃止）**:
  - ルート側の既存コードのように言語別（`_JA`, `_EN`）でシナリオ定義（モーション・カメラ・分岐等含む）丸ごとを重複定義することは禁止とする。
- **単一インスタンス内での多言語保持**:
  - 1つのシナリオ定義オブジェクト内でテキストを管理する。
  - 方式: `text: { ja: string; en?: string }`（または `text_ja` / `text_en`）、あるいは i18n 辞書キー（`dialogue.day1.morning.01`）への参照を採用する。
  - 演出・モーション・カメラワーク・フラグ分岐ロジックは常に1つに統合され、テキストやボイスURLのみを言語設定に応じて切り替える構造とする。
